# R4 dated SWE-bench Verified leaderboard replay protocol (2026-10-12)

This is a retrospective exploratory replay. The two April 2024 matched-pair outcomes in `PUBLIC_REPLAY_03_RESULTS.md` are already known. For the remaining submissions, only source directory names, file paths, and the existence of `metadata.yaml` and `results/results.json` were inspected before this protocol. Source: `SWE-bench/experiments` revision `40f164d5b8f1d249bf95a6df8b74b577fd8e519d`, `evaluation/verified/`. The repository has no root license statement found in the prior audit; cache source JSON locally but do not commit it.

## Population and chronological rule

- The unit is one date-stamped submission directory with `results/results.json`. Sort by the eight-digit prefix in the directory name, then by the complete directory name. The prefix is a *directory date*, not verified submission or public-release time. Count and report all directories, missing result files, and exclusions.
- Parse result status lists as in `public_replay_03.py`. Deduplicate repeated IDs within a status list. Exclude a submission with malformed statuses, an ID in both `resolved` and an adverse status, or fewer than 490 distinct reported Verified IDs. Determine the fixed universe as the union of IDs in the eligible submissions, require exactly 500 IDs, and reject any submission with an ID outside it. Score absent IDs as unsuccessful on the 500-ID universe; report how many are absent. The threshold and missing-as-failure rule are fixed before inspecting results.
- The first eligible submission is the initial running leader. At each later eligible entry, compare its 500-task score to the current leader's score. A strictly higher score is a *reported-score leader claim*. Update the running leader to that entry whether or not it crosses an e-value boundary; ties keep the earlier leader. This mimics a displayed leaderboard ranking and keeps the comparison rule mechanical. Every eligible entrant, including those without a score increase, receives a comparison row. No model- or scaffold-matching filter is applied: the unit is the whole agent system.

## Sequential replay and readings

- Use the repository's binary incumbent-relative E1b process on the 500 paired outcomes, in one task order per entrant from `SeedSequence([20261012, 44, entrant_index])`, where entrant index is 1-based among eligible entries after the initial leader. An entrant's comparison uses the leader *before* any update on that entrant. Report first crossing under nominal `alpha=0.05` and under a fixed entrant-index spending sequence `alpha_j=0.05/[j(j+1)]`. The spending sequence sums to less than 0.05 over all future entrants; it is a descriptive sensitivity analysis here, not a familywise error guarantee under adaptive benchmark reuse.
- For score-increase claims, report the paired gain, discordant wins/losses, the fraction crossing each threshold, crossing-time distribution, full-grid versus stopped paired episodes, and cases where a displayed score increase does not cross. Report all entrants separately from leader claims. Treat a crossing on a score-decrease comparison as an anomaly to investigate, not as a leader claim.
- All comparisons reuse the same historical 500 tasks. Task order is synthetic, and submissions were likely developed using earlier public feedback. Selection of the running leader from these tasks and adaptation of later systems to the benchmark invalidate a prospective anytime-valid or independent familywise interpretation. The original two prespecified matched-system comparisons remain the narrow evidence for early detection; this replay addresses only the historical leaderboard question.

## Decision rule for the manuscript

Include R4 in the framework manuscript only as a descriptive audit of when displayed score leaders would have crossed under a frozen task order. If coverage, dates, or record semantics make a clean 500-task chronology infeasible, report the failure and keep the matched-pair account instead. Do not turn a displayed ranking into a claim of causal model or scaffold improvement.

## Post-inspection source-format amendment (2026-10-12)

The strict first pass found only 12 of 135 result files with at least 490 IDs. On inspecting the source's own `analysis/get_results.py` and `analysis/get_leaderboard.py`, we found why: recent `results.json` files are deliberately sparse, containing resolved IDs and a few failure categories, while the official leaderboard computes `len(resolved)/500`. An omitted ID is therefore scored unsuccessful in the published rate. This explanation was learned **after** the strict replay loaded result files, so the extension below is exploratory and must be reported alongside the registered strict result.

Reanalyse all well-formed result files with the official `resolved`-list semantics, using the same fixed 500-ID universe, absent-as-failure scoring, chronology, E1b task-order seeds, and thresholds. Exclude malformed or out-of-universe files, and report coverage and missing-ID counts. Keep metadata-only entries out of itemwise inference because they lack released resolved-ID lists. The extension is a descriptive reconstruction of the official score scale, not a new preregistered validation of sequential inference.
